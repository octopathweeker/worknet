# Worknet 平台化与 EIP-7702 分阶段计划

日期：2026-09-19。状态：执行基线。用户已授权先完成 R2+R3，再 Human 验证；部署与验收进展见[阶段状态](PROJECT-STATUS.md)。下文的门槛是计划要求，不能视为已完成证据。

基线：[R1 summary](PROJECT-STATUS.md)、[R1 handoff](PROJECT-STATUS.md)、[M5 summary](PROJECT-STATUS.md)。历史阶段作为当时验收快照保留。本计划将原设计中的可选 7702 研究提前到下一阶段，后续技术选型以 R2 实验结果为准。

## 1. 产品目标与解释

真实用户可直接在平台上作为 requester 发布任务；其他真实用户可通过自带 harness 或平台 GUI 作为 taker 参与。同一个用户可以兼具两种角色。Workspace 成为可选团队容器，用户、钱包、执行器、任务和授权分别建模。

根据阶段 summary/handoff 的上下文，本计划将“分阶段执行”解释为分阶段研发交付。业务任务的 milestone、分段付款、任务依赖图属于另一项协议能力，不能把它们等同于本计划的研发阶段。

暂定第一版以已有 EVM 钱包的用户、Monad Testnet、公开任务、现有研究与 Transfer 分析能力为起点。GUI taker 包含选择任务、授权执行、查看过程和提交结果；用户手工交付、自带 harness、平台托管 Agent 的具体优先级尚待确认。计划保留托管 GUI 阶段，手工交付如纳入，需同时设计适合人工的交付和审核时间。

## 2. 已核对的 7702 事实

- Monad 支持 EIP-7702，可由他人提交用户签署的委托；EOA 保留地址，并执行所委托账户实现的代码。
- 7702 为批量操作、gas 代付和受限权限提供基础；session key 的权限、预算和有效期仍由账户实现或模块验证。7702 委托自身持续存在，直至更换或清除。
- Monad 对 delegated EOA 的原生 MON 余额减少有特殊限制。低于 10 MON 并不意味着账户不能使用：赞助交易若不减少该账户的 MON 余额，仍可工作。不得把 10 MON 写成注册押金。
- 委托代码在 EOA 上下文中不能直接执行 CREATE/CREATE2；如需创建 Vault，应评估由独立 Factory 合约执行创建。

以上来源：[Monad EIP-7702](https://docs.monad.xyz/developer-essentials/eip-7702)、[Reserve Balance](https://docs.monad.xyz/developer-essentials/reserve-balance)。

委托签名不等于对某次业务操作的签名；执行授权须绑定操作及防重放信息。委托处理与后续调用的失败语义也不同：业务调用回滚不保证已处理的委托回滚。钱包应选择并审查账户实现，平台应通过其支持的能力与模块集成，不能假设任何扩展钱包都允许 DApp 指定任意 delegate。[EIP-7702 标准](https://eips.ethereum.org/EIPS/eip-7702)

## 3. 推荐账户架构

第一轮采用“7702 账户体验 + 独立 RequesterVault 预算边界 + 现有 TaskManager”。

### Requester

用户钱包拥有其独立 Vault。7702 优先用于用户确认的批量充值/授权和 gas 赞助。自动发布、审核继续经该用户明确授权的 requester operator 及 Vault 执行，保留单笔限额、累计 commitment、epoch 和恢复语义。

账户抽象层与业务预算层分开，不在这一轮把 Vault 的预算逻辑迁移到新 delegate。当前 Requester SDK 强绑定 config.vault，需要抽出账户适配层和租户路由；不是切换一次 RPC 即可完成。

现有 Vault 的 Owner 可接管审核，且此路径不依赖 Agent epoch。如果后续让 session key 通过 Owner EOA 执行操作，必须在账户层另行约束与撤销，不能宣称 Vault 的 Agent 撤销自然覆盖 Owner 路径。Reviewer-only 权限若需要单独开放，应单独设计，当前 Agent 权限同时覆盖发布与处理结果。

现有 RequesterVault 含 constructor/immutable owner 等部署假设，不能直接用作用户 EOA 的 7702 delegate。

### Taker

候选流程：harness 持受限 session key，账户验证授权后，由用户 EOA 调用 TaskManager 的 claim/submit。这样链上 worker 和奖励收款方仍是用户地址，harness 的进程或 session key 不成为奖励所有者。

权限至少约束链、目标合约、允许操作、任务/attempt 范围、期限、nonce 和并发策略。submit 须受已领取任务绑定约束；不能只检查方法名。多个执行器共享一个钱包时，要协调执行 nonce 与已有 claim，不能沿用“每个 harness 都拿同一主私钥独立签名”的方式。

交易赞助服务只支付允许的操作，验证用户身份、操作授权、限额与幂等。Gas 由赞助者实际承担，不能描述为没有成本。Harness 接入 token、session key、用户主钱包私钥是不同凭证。

### 普通钱包兼容

支持普通钱包手动签名作为接入路径。7702 钱包能力须检测并明确展示，不默默改成平台托管签名。普通路径可用不能代替 R2 的真实 7702 验收。

## 4. 阶段与验收

阶段按 R2 → R3 → R4 → R5 → R6 推进。每阶段交付实现、必要验证、summary 和 handoff 后再进入下一阶段；发现关键兼容问题时记录具体阻塞，不以 mock 或前端截图替代验收。

### R2 — 7702 账户路径验证与设计冻结

目标：先验证用户实际能使用的账户路径，避免平台层建立在未经确认的钱包能力上。

交付：

1. 选定一个真实钱包与账户实现/权限模块组合，记录版本、支持网络、委托与 session 授权接口、可用部署与审查依据。优先采用钱包支持的成熟实现；官方示例地址不自动视为可用账户产品。
2. 建立隔离的 Testnet 验证环境，保留 R1 现有任务和对象地址。
3. 验证 requester 的批量操作/赞助与独立 Vault 路径；验证 taker 以用户地址执行 claim/submit 并收取奖励。
4. 冻结普通钱包、7702、Vault、session 与 relayer 的职责和接口，以及失败恢复策略。

门槛：真实钱包参与授权；Testnet 交易 receipt 和余额证明调用/收款归属；赞助者 gas 支出与用户 MON 余额可核对；越权、重放、过期、撤销后执行被拒绝；验证调用失败但委托可能仍生效的恢复。覆盖低 MON 余额赞助场景，并对 Monad 余额限制和 Factory 创建路径留下针对性证据。无法实际覆盖的项目列为未完成。

输出：`docs/stages/R2/summary.md`、`handoff.md`、账户决策与实验脚本、脱敏验证证据。当前状态以 R2 summary 为准。按用户后续指令，真实浏览器钱包的 Human 验证在 R2+R3 工程交付后统一执行。

### R3 — 独立用户与 requester 平台闭环

目标：新用户无需工作区访问码或本机配置，可在平台发布自己的任务。

交付：钱包登录与签名校验、用户/钱包绑定、独立 Vault 初始化与授权流程、按用户划分的计划/命令/预算/任务、公开平台 API、链上索引、持久命令队列和常驻 reviewer。最小的平台服务部署在独立运行环境，不依赖当前开发电脑出站 bridge；执行 Worker 此时可沿用已验证执行器。

门槛：两个独立用户分别充值/授权/发单；双方不能操作彼此的资金或私有草稿；重复提交不重复创建或扣款；服务重启能恢复；关闭当前开发电脑后仍能发布、查询及处理结果。已公开上链/存储的数据不冒称私密。

输出：`docs/stages/R3/summary.md`、`handoff.md` 和双用户证据。当前状态以 R3 summary 为准。

### R4 — Taker GUI 与外部 harness 接入

目标：外部用户通过自己的设备和执行工具参与，不需要平台管理员凭证。

交付：任务大厅、领取与提交 GUI、执行器注册/配对/撤销、taker API/CLI/MCP、统一执行 adapter、任务级上传授权、执行进度与收益。GUI 和 harness 共用业务状态与权限。先接通一种 harness，再用第二种验证抽象，具体 harness 尚待选择。

门槛：另一台设备上的真实 taker 完成发现→领取→执行→提交→收款；两个 harness 的真实集成有证据；断线/恢复不重复领取或提交；多个执行器不会争用同一个签名 nonce；不共享访问码、主私钥和全局上传凭证。若 handoff 包含等待付款的任务，必须记录当前 attempt/hash 与恢复动作。

输出：`docs/stages/R4/summary.md`、`handoff.md`、接入指南与跨设备证据。当前状态：工程与 Testnet 验证完成，真实扩展钱包和客户端 Human 验证待完成。

### R5 — 平台托管 GUI 执行

目标：用户只通过浏览器即可选择并驱动平台提供的 Agent。

交付：托管执行队列、任务隔离、模型/工具接入、运行日志、产物、资源限额、成本展示与取消语义。明确奖励收入、模型/工具成本和 gas 成本的归属；不把平台自有执行器的收益显示为用户个人收益。延用 R4 的执行 adapter，平台 runner 作为一种执行方式接入。

门槛：用户在没有本地 daemon/harness 的设备上通过 GUI 完成完整任务；至少两用户并发且执行/产物/凭证隔离；模型或执行器失败不会伪报成功、误提交或重复付款；用户能区分停止计算与链上 claim 的到期/释放。具体模型和托管资源在本阶段选择时确定。

输出：`docs/stages/R5/summary.md`、`handoff.md` 和纯浏览器实测证据。当前状态：工程、部署、双用户浏览器软件钱包 Testnet 验证及桌面/移动截图检查完成；真实扩展钱包与独立设备 Human 验证待完成。

### R6 — 开放试用与市场规则验收

目标：验证陌生用户之间的任务闭环与运行恢复，形成可交付版本。

交付：补齐任务与执行器筛选、通知、审核超时说明、赞助限额、异常恢复和运行手册；明确哪些规则由平台执行，哪些由链上强制执行。界定抢单、公平验收和争议边界。需要指定 taker、准入、押金或改变超时付款时，另立协议变更并验收，不能仅靠 UI 宣称实现。

门槛：多用户端到端与钱包兼容回归；无人接单、lease 超时、错误提交、审核离线、session 撤销、赞助服务离线、执行器恢复均有证据；用户主钱包不暴露给平台或 harness；阶段闭环与残留任务/资金全部可核对。

输出：`docs/stages/R6/summary.md`、`handoff.md`、验收报告和已知限制。当前状态：工程、部署、本地故障矩阵与公网 API 验收完成；真实钱包、独立设备和陌生用户 Human 试用待完成。本阶段不自动代表主网或生产安全审计通过。

## 5. 阶段执行约定

- 每阶段只按其门槛报告已实现、已测试、已部署和未完成事项。
- 已授权的阶段内实现、修复和必要验证持续推进；阶段交付不额外制造重复确认。钱包交互或新增外部资源确实需要用户参与时，说明具体依赖。
- `summary.md` 记录最终交付和实际证据；`handoff.md` 记录下一步顺序、运行配置来源、现存部署和恢复事项。凭证不进入文档。
- 沿用 request ID、attempt/hash 绑定及签名 outbox 的幂等语义；账户类型改变时重新验证，不能直接复制单 signer nonce 假设。
- 旧 TaskManager、Vault 和内容 URI 保留。新账户/部署先独立验证；切换需确保旧任务仍可审核、退款和结算。
- 当前执行状态见 PROJECT-STATUS 和各阶段 summary；R6 已获授权推进，工程交付后继续 Human 验证；未覆盖的真人与设备门槛必须单独保留。
